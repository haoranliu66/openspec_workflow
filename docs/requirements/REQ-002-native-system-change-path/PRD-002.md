## 用户与旅程

| 角色 | 当前痛点 | 目标旅程结果 |
|---|---|---|
| 工作流使用者 | 有限的新系统行为既不是 Bug，也不值得创建完整共享产品需求包 | 选择 system-change，以原生 spec-driven 规划、授权、实施并正式关闭 |
| AI | “改动规模小”与“产品语义小”容易混淆 | 依据产品治理面和行为性质选择互斥路径，范围扩大时升级 |
| 维护者 | 直接使用 spec-driven 会被当前 closeout 和历史治理判为未知 Schema | 内置 Schema 被识别、校验、归档并进入确定性历史 |

## 产品范围

- **范围内**：`system-change` 路径名称与判定规则；实际使用内置 `spec-driven`；授权停顿；稳定 Requirement ID；非产品 closeout；formal close、索引与安装目标支持。
- **范围外**：复制或修改 OpenSpec 原生 Schema；为 system-change 创建共享 BR/PRD/FEATURE；把产品变化按代码量降级；取消原生 design artifact。
- **依赖**：OpenSpec `1.5.0` 内置 `spec-driven` Schema、本项目现有 closeout 与 archive wrapper。

## 产品规则

- bugfix 只用于恢复已经确认的行为，且不产生新的产品或系统 Requirement。
- system-change 用于新增或修改有限的系统可观察行为，同时不改变产品目标、用户旅程、角色权限、业务规则、公共接口契约，也不需要共享产品验收。
- product-change 用于任何需要产品发现或共享验收的变化；角色权限、业务规则、公共接口、显著数据或迁移变化即使代码量很小也不得降级。
- 纯实现重构或格式调整若不改变可观察行为，不得仅因工作量大小创建虚假的行为 delta。
- system-change 是治理路径名，change metadata 必须直接写 `schema: spec-driven`；仓库不得复制一个别名 Schema。
- 原生 graph 保持 `proposal -> {specs, design} -> tasks -> apply`；小改动可使用简洁 design，但不能绕过其依赖闭包。
- system-change 不使用共享 BR/PRD/FEATURE；closeout 使用 `version`、evidence 和四项 gates，并要求所有 delta Requirements 有稳定 ID。
- system-change 规划包完成或实质修改后，仍执行 change-scoped 明确授权停顿。
- `workflow close <change>` 必须对 spec-driven change 执行 strict/closeout validation、OpenSpec archive、索引重建和治理检查。
